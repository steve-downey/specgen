Every command below is a script in [[file:../examples/cli][=examples/cli/=]], and every output below is what that script printed.
Both are transcluded from the repository, so neither is retyped here, and neither can drift from the other without a test detecting it.

Running the scripts requires the binary.
=make install-release= installs it at =.install/bin/specgen=, which is where the scripts look for it; =SPECGEN= names another location, such as a build tree.
Every build of specgen includes the Clang front end, so every command here works with any binary.

#+begin_src sh
make install-release          # or: export SPECGEN=<build tree>/tools/specgen/specgen
examples/cli/run-all.sh       # re-capture everything shown below
#+end_src

=run-all.sh= rewrites the checked-in output, and =ctest -R examples.= checks it.
Most of those checks compare a captured file against the golden suite; the remainder re-run a script and compare its output.
The output shown here is therefore not an illustration of what specgen does, but a record of what it did.

The ordinary way to use specgen is a single =generate= command, which parses a header and renders its wording in one process.
Several examples instead use =generate --emit-ir= and =render --from-ir=, which write and read specgen's JSON intermediate representation.
That route is a debugging aid rather than an authoring workflow, but it lets an example render a fixed, checked-in IR fixture from the golden suite, so that only the option under demonstration varies.

* A Paper Of Several Headers
:PROPERTIES:
:CUSTOM_ID: a-paper-of-several-headers
:END:

A paper proposing several headers is several specgen documents and one invocation.
=generate= takes one header per document and validates across the union of their documented names, so a name specified by a sibling document is not foreign.
It writes the assembled clause, the per-clause fragments, or both.

#+transclude: [[file:../examples/cli/55-paper.sh]] :src sh

=--split= names the pieces, in document then section order:

#+transclude: [[file:../examples/cli/output/55-paper/manifest]] :src text

=-o= names the whole, which consists of the same pieces in the same order without the fragment boundaries.
=golden.paper_whole.is_fragments= verifies this, because a paper that assembles its clause from fragments and one that renders it whole must agree.

=--depfile= writes what make needs to know to rebuild any of it.
The prerequisites are every file the parses read.
They include =include/support/spec_paper_traits.hpp=, which neither header names on the command line and no rendered wording mentions; it is nevertheless the dependency that matters most, because a docblock in it changes the generated clause, and a paper that did not depend on it would become stale without notice.
The empty rule per prerequisite corresponds to =-MP=: when a header is deleted or renamed, the next build regenerates the wording rather than failing on a prerequisite that no longer exists.
